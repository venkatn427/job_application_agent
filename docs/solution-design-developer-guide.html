01 / Scope & Status

Revision 1.1 implementation update: the original review snapshot below is retained for traceability. Preparation now creates prepared records without applied timestamps or follow-ups; canonical job URLs are preserved. Live AutoApplier calls require explicit approval, default to dry-run, and the dashboard asks for confirmation. API dry-runs skip upstream preparation. Dashboard preparation uses JobListing and returns an error if no resume exists. Empty profiles stop the batch pipeline. Partial key updates preserve existing keys using atomic mode-0600 writes. Flask is restricted to loopback/same-origin JSON requests with debug disabled; this is local hardening, not multi-user authentication. Foreign keys are enabled per tracker connection. These changes have offline regression coverage in tests/test_safety_regressions.py. Historical records are not automatically relabeled; review legacy applied records manually.

The repository is a local-first Python application with multiple entry points, not a single unified service. The batch pipeline prepares application packages. Separate Flask and CLI paths support tracking and browser-based submission. A second Streamlit application and MCP tools coexist with these paths.

Readiness assessment: suitable for supervised local development, with production blockers around submission consent, tracking accuracy, endpoint protection, retries, and shared data contracts. Earlier smoke-test pass counts do not establish end-to-end correctness.

03 / Processing Flows

A. Batch Preparation: Actual Call Order

  1. Load profileRead valid cache or extract resume/export and parse with Claude.
  2. Fetch jobsConfigured sources, queries, locations and excluded titles.
  3. Remove duplicatesIn-fetch dedup plus processed_jobs lookup.
  4. Score and splitCompute MatchResult; mark below-threshold jobs skipped.
  5. Build packagesFor each match, tailor resume; build PDF/DOCX, optional cover letter and analysis.
  6. Publish and recordAttempt Drive and Sheets; mark matched; notify; write run log/report.

Important: this flow prepares documents; it does not apply. Optional cloud failures do not prevent the job being marked matched. Failed jobs are retried next run; matched and skipped jobs are excluded.

B. Dashboard Preparation

POST /api/jobs/prepare
  -> validate title/company
  -> construct minimal job object
  -> attempt Claude tailoring, otherwise master PDF fallback
  -> call AppTracker.add_application()
  -> return local paths, app_id, keywords, ai_tailored flag

Current discrepancies: the minimal job lacks requirements, which the resume generator reads; the catch-all fallback can hide that error. Tracker insertion marks a merely prepared job as applied, and the response can remain ok: true even without a resume file.

C. Optional Browser Submission

POST /api/jobs/apply
  -> create in-memory task ID -> launch daemon thread
  -> optional portal credential lookup
  -> ResumeAdapter.prepare() or master-resume fallback
  -> AutoApplier.apply(url)
       dry_run=true: return without browser launch
       otherwise: detect platform -> launch Chromium -> fill/submit adapter
  -> store task result in process memory
GET /api/jobs/apply/<task_id>/status -> poll task

API task status done means the worker returned, not necessarily that submission succeeded. Check result.success. Task state is lost on restart, and this handler does not persist a confirmed application outcome to AppTracker.

05 / Matching & AI

ComponentMaximumInput
Keyword overlap40Known JD keywords matched to normalized profile skills.
Title alignment20Job title compared with candidate titles.
Experience20Inferred required years / seniority versus profile experience.
Domain alignment10Candidate domain evidence versus job text.
Claude analysis10Optional bonus and qualitative gaps/topics.
base = keyword + title + experience + domain
if use_claude AND api_key_present AND base >= threshold - 15:
    bonus, interview_topics, gaps = Claude analysis
score = min(100, base + bonus)
recommended = score >= threshold

The implementation can produce zero, despite the requested 1-100 scale. Without Claude, the ceiling is 90. Required qualifications are not hard rejection gates; absent mandatory credentials can still yield a high score. Calibration against real recruiting outcomes is not present.

Resume Rules and Trust Boundaries

Prompts instruct Claude not to invent skills, employers, dates, or metrics and to use one page below five years and two pages otherwise. System/profile prompt blocks use ephemeral cache hints. Cache hits and savings depend on provider behavior and payload eligibility; they are not a fixed percentage guarantee.

Generated JSON is parsed and empty experience sections can fall back to original bullets. PDF/DOCX builders render the result but do not measure and enforce final page limits. Treat scraped descriptions as untrusted data, never as instructions. Human review is still necessary before using generated documents or screening answers.

Claude is the implemented provider. An interchangeable OpenAI/Claude provider layer is a proposed enhancement, not current functionality. Model strings in source are configuration defaults, not verified current provider availability.

09 / Operations

Current YAML schedules a daily run at 08:00 America/Los_Angeles, not the user's America/Chicago timezone. Weekly analytics runs Sunday at 09:00 in the configured scheduler timezone. Set the timezone explicitly if Central time is intended. The scheduler must remain running and has no durable job store configured.

ConcernCurrent State / Operator Action
ConcurrencyMain matched-job processing is serial. scheduler.max_concurrent is not wired to worker concurrency. Dashboard apply creates unbounded daemon threads.
ReprocessingMatched/skipped jobs are suppressed indefinitely by ID; profile or threshold changes do not re-evaluate them. Design explicit rescore/version policies rather than deleting production history.
ReportsBatch writes logs/run_YYYY-MM-DD.txt; same-day runs overwrite that report. Database preserves separate run rows.
BackupsBack up SQLite with a transaction-aware backup operation, generated artifacts, settings and profile sources. Protect personal data; keep encryption-key backups separate and access-controlled.
RecoveryRetain failed-job diagnostics. Verify artifacts before retrying, since partial cloud uploads and tracker writes may already exist.
ObservabilityPython logging, run counts and text reports exist. Add run/job IDs, per-stage timings, source-error counts, sync status and audit events.

Troubleshooting

  • No matches: inspect profile content, source errors, title exclusions and scoring components before lowering threshold.
  • Master resume returned instead of tailored: inspect dashboard warnings; a key's presence does not prove tailoring succeeded.
  • Drive/Sheets not updated: check identity permissions, spreadsheet/tab IDs and logs; matched status does not guarantee cloud success.
  • Task disappeared: dashboard apply task state is in memory and disappears on process restart.
  • Repeated or missing applications: compare pipeline.db, applications.db, CSV and submission logs; they are not a unified audit trail.

10 / Security

Candidate resumes, contact information, work authorization answers, browser credentials and generated documents are sensitive. Resume and job text are sent to Claude when enabled; cloud artifacts go to Google and notifications may disclose job/profile details to additional services.

  • Keep Flask bound to loopback. The server enables broad CORS and debug mode, and sensitive mutation routes lack authentication. Do not expose it publicly without authentication, authorization, CSRF/origin protection and hardened serving.
  • Rotate any credentials previously exposed in chat or terminal history. Keep secrets out of version control, generated HTML, screenshots and application logs.
  • Portal passwords use Fernet encryption with a local data/.portal_key created mode 0600. Encryption is not protection against compromise of both DB and key on the same host.
  • Validate and constrain submitted URLs before requests or browser navigation. Block local/private network targets and unsupported schemes to reduce SSRF exposure.
  • Set explicit dry-run controls during development. Browser automation must require deliberate submission approval; playbook instructions do not enforce controls in a separate Python path.
  • Do not infer consent, work eligibility, demographics, salary or legal declarations from missing data. Escalate unknown screening answers to the candidate.
  • Use least-privilege Google scopes and retention/access policies for profile caches and output folders. Current Drive scopes include full Drive access.

11 / Code Review Findings

Findings below preserve the original review snapshot. See the Revision 1.1 implementation update in Scope & Status for fixes now implemented. Remaining work includes durable task state, cloud retries, pagination/backoff, artifact identity, evidence validation, settings enforcement and comprehensive SSRF protection. P1 denotes a high-priority correctness or safety issue; P2 denotes a material reliability or maintainability gap.

P1 · Preparation recorded as application

prepare_job() calls add_application(), which hardcodes status='applied' and an application timestamp before any submission. This corrupts application counts, response metrics and follow-up timing.

Fix: introduce prepared/pending states and set applied only after confirmation evidence. Store preparation and submission timestamps separately.

Evidence: api_server.py:581; app_tracker.py:234. Tracker default confirmed with an isolated temporary database.

P1 · Live submission default; inconsistent approval controls

AutoApplier defaults AUTO_APPLY_DRY_RUN to false when no explicit flag is supplied. The Flask apply route passes missing dry_run as None. Submission-helper settings and playbook approval guidance are not a central enforcement gate here.

Fix: default to dry-run; require explicit approved submission intent per job; record consent and enforce run caps in the submission service.

Evidence: auto_apply.py:705; api_server.py:1201.

P1 · Sensitive API operations are unprotected

Key writes, profile changes, portal management and browser submission have no authentication middleware; CORS is broad and debug mode is enabled. Loopback binding limits exposure but does not make this a deployable multi-user API.

Fix: authenticated local session, strict origins, CSRF protection, URL allowlists, validated request schemas and production server configuration.

Evidence: api_server.py:46, api_server.py:743, entry point at end of file.

P1 · Dashboard job contract breaks tailoring

The dashboard constructs an ad hoc job object without requirements. ResumeGenerator._jd_to_prompt() accesses that field. The error is caught and may silently degrade to the master resume while the endpoint still reports success.

Fix: instantiate JobListing with validated defaults; return explicit tailored/fallback/failed outcome and require an existing output file.

Evidence: api_server.py:523; resume_generator.py:335.

P2 · Application URLs dropped at the tracker boundary

JobListing exposes apply_url, but AppTracker reads job.url. Passing a canonical listing stores an empty job URL. The dashboard's ad hoc object masks the mismatch by setting both fields.

Fix: use one canonical URL contract and add a cross-module contract test.

Evidence: apify_scraper.py:40; app_tracker.py:227. Reproduced with a temporary database and apply_url-only object.

P2 · Empty candidate profile does not stop the pipeline

Parsing errors return an empty profile, and processing continues. Poor scores can then be stored as skipped and suppressed in future runs even after the candidate profile is corrected.

Fix: enforce minimum profile validity before fetching/scoring, and version dedup decisions by profile and scoring policy.

Evidence: workflow.py:251 and workflow.py:320.

P2 · Retry, pagination and sync completion gaps

Apify reads a dataset with one unpaginated request and lacks general HTTP backoff. Drive/Sheets errors can be swallowed while jobs become matched, so the next run will not retry those uploads.

Fix: pagination with explicit completion; bounded retries honoring Retry-After; persistent artifact and sync stages independent of matching.

Evidence: apify_scraper.py:81, apify_scraper.py:118, workflow.py:395.

P2 · State, filenames and idempotency are fragmented

PipelineDB, CRM, Streamlit and MCP stores are separate. CRM has no unique job-identity constraint; company/title output names collide. Process-local task threads are neither durable nor bounded.

Fix: unify job/application IDs, use versioned job-ID artifact paths, add unique idempotency keys and a persistent bounded task queue.

Evidence: app_tracker.py:48; workflow.py:369; api_server.py:1170.

P2 · Settings and dependency declarations overstate behavior

PipelineConfig reads required_keywords, min_salary and job_types, but the fetch workflow does not apply them. scheduler.max_concurrent is unused. Root requirements omit Flask, flask-cors and Playwright even though new entry points import them.

Fix: wire or reject unsupported settings; declare entry-point dependency groups and lock tested versions.

Evidence: workflow.py:86, workflow.py:334, scheduler.py:125, requirements.txt.

P2 · Evidence and document rules are not machine-enforced

No deterministic validation proves generated claims or metric provenance. Resume page targets are prompt-only. Profile cache invalidation checks resume changes, not LinkedIn-export changes. ScreeningMemory and advisor outputs need candidate-approved boundaries.

Fix: evidence IDs for candidate claims, schema validation, prohibited-claim checks, rendered page-count tests, and hashes for all profile sources.

Evidence: resume_generator.py:159; profile_analyzer.py:255; apply_engine.py:200.

P2 · Partial API-key updates remove unrelated persisted keys

save_keys() removes all allowed keys from the existing .env and re-adds only nonempty keys in the request. Updating one key can erase other persisted keys while leaving their old values in process memory, producing different behavior after restart.

Fix: merge explicitly supplied keys, define explicit deletion semantics, validate values and write atomically with restrictive permissions.

Evidence: api_server.py:744.

13 / Extension Guide

Add a Job Source

  1. Implement an adapter returning list[JobListing] with complete description, stable source ID and canonical application URL.
  2. Register it in JobFetcher and define query/location/result-limit behavior. Return typed errors rather than hiding failures as zero jobs.
  3. Add response fixtures, pagination, rate-limit and malformed-response tests; document credentials and permitted use.
  4. Expose the source consistently in YAML, API and UI; avoid a second independent scraper implementation.

Add a Submission Platform

  1. Extend platform detection and the adapter registry in submission/auto_apply.py.
  2. Implement the existing page/profile/resume/cover-letter/credentials interface, but centralize approval checks outside adapters.
  3. Use approved candidate answers; unknown mandatory fields must stop the flow.
  4. Require positive confirmation evidence, redact diagnostics and test against local forms before any approved real submission.

Change Matching or Add an LLM Provider

Keep scoring deterministic by default; version score policy and record component scores. Introduce a narrow provider interface for structured profile parsing, resume drafting and optional semantic analysis. Validate a common output schema and evidence constraints regardless of provider. Keep model choice/configuration outside business logic.

Developer Conventions

Prefer existing dataclasses over ad hoc objects; share domain contracts across CLI and API; use UTC for persisted events and explicit display timezones; record IDs in every log; keep secrets and candidate content out of fixtures; separate network work from database transactions. Preserve unrelated worktree changes during implementation.
